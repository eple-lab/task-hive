# 08. 성능 검토 화면

작성일: 2026-11-17 · 근거: [D-09](02-decisions.md) (운영 지표 + PoC 검증, 숫자만). 세부 구성은 제안이다.

## 1. 목적

| 질문 | 답하는 탭 |
|---|---|
| 지금 서비스가 빠르고 안정적인가 | 운영 지표 |
| AI를 넣어서 실제로 나아졌는가 (메인 퀘스트의 "개선 효과 검증") | PoC 검증 |
| 보안 규칙이 일하고 있는가 | 보안 신호 |

## 2. 원칙

- 본 화면과 **별도 주소**(`/admin`), 별도 파일(`static/admin.html`)이다.
- 관리자만 본다(P-15). 일반 사용자와 손님에게는 없는 주소처럼 보인다(404).
- **대화 내용, 태스크 제목, 일기, 사용자 구분 값을 담지 않는다.** 숫자와 종류만 모은다.
- 지표는 30일 뒤 지운다.
- 관리자 화면이 뚫려도 개인 데이터가 나오지 않게 만든다.

## 4. 운영 지표 탭

### 4.1 숫자 타일

| 지표 | 뜻 | 목표 (제안) |
|---|---|---|
| 첫 글자까지 걸린 시간 | 보내기부터 답의 첫 글자까지 (중앙값, 95% 값) | 중앙값 3초 이하 |
| 초당 토큰 | 답이 나오는 속도 | 15 이상 |
| TTS 지연 | 문장을 보낸 뒤 소리가 시작되기까지 | 1.5초 이하 |
| STT 지연 (2단계) | 녹음 끝부터 글이 나오기까지 | 녹음 길이의 절반 이하 |
| 오류율 | 실패한 요청 / 전체 | 5% 이하 |
| 활성 세션 | 최근 15분 안에 요청한 세션 수 | - |

### 4.2 그래프와 표

| 항목 | 내용 |
|---|---|
| 응답 속도 추이 | 시간대별 첫 글자까지 걸린 시간 (중앙값, 95% 값) |
| 기능별 호출 수 | 대화, 추출, 말하기, 받아쓰기, 캘린더, 일기 저장, 벌집 등록 |
| 오류 종류 | 업스트림 연결 실패, 시간 초과, 추출 JSON 형식 오류, 구글 API 오류, 시트 반영 실패 |
| 대체 음성 사용률 | Colab TTS 대신 브라우저 음성으로 읽은 비율 |
| 외부 서비스 상태 | Neon, Google API, 날씨의 최근 성공 여부와 응답 시간 |
| 서버 상태 | 메모리 사용량(512MB 대비), 서버가 깨어난 횟수와 깨어나는 데 걸린 시간 |
| 정리 작업 | 지운 손님 행 수, 지운 완료 태스크 수, 마지막 실행 시각 |

ngrok 주소가 사용자마다 달라(D-04) 업스트림 속도는 사용자 Colab의 상태에 좌우된다. 이 화면은 전체를 합친 숫자만 보여 주고, 주소별로 나누지 않는다. 사용자가 자기 Colab 속도를 보는 것은 [07 Q-18](07-open-questions.md).

## 5. PoC 검증 탭

메인 퀘스트의 "개선 효과 검증"을 화면으로 보여 준다. 데이터는 실제 사용자 대화가 아니라 **검증용 가상 대화**(`eval/samples/`)를 `eval/run_eval.py`로 돌린 결과(`eval/results/*.json`)다.

검증 규칙 (수업 「내 업무 어디에 AI를 넣을까?」 기준):

- 정답(기대하는 할 일)은 **모델을 돌리기 전에** 적는다. 결과를 보고 정하지 않는다.
- 가상 대화는 10~20건. 그중 3~4건은 어려운 것으로 넣는다(부정문, 남의 일, 애매한 날짜, 할 일이 없는 대화).
- 성공 기준 숫자의 근거는 지금 사람이 하는 수준이다. 기존 방식(`todo` 앱 직접 입력)을 먼저 잰다.
- 점수는 반올림하지 않고 기록한다. 결과 파일은 다시 돌려도 덮어쓰지 않는다.
- 기준을 못 넘으면 "못 넘음"과 이유를 그대로 적는다.

### 5.1 할 일 추출 정확도

후보마다 **근거가 된 대화 문장**을 함께 보여 준다. 틀렸을 때 사용자가 원문에서 바로 확인할 수 있어야 한다. 확신이 낮은 후보는 "확인 필요"로 표시해 사용자에게 넘긴다.

| 지표 | 뜻 |
|---|---|
| 정확히 뽑은 비율 (정밀도) | AI가 뽑은 후보 중 실제 할 일인 비율 |
| 놓치지 않은 비율 (재현율) | 실제 할 일 중 AI가 뽑은 비율 |
| 날짜 정확도 | "다음 주 금요일" 같은 말을 맞는 날짜로 바꾼 비율 |
| 완료 신호 정확도 | "그건 한 것 같아"를 맞는 태스크에 연결한 비율 |
| 지어낸 할 일 수 | 대화에 없는데 뽑은 것 |

표: 샘플별로 기대한 할 일, AI가 뽑은 할 일, 맞음/틀림. 가상 대화라서 내용을 보여 줘도 된다.

### 5.2 기존 방식과 비교

| 비교 | 기존 방식 | Task Hive |
|---|---|---|
| 같은 할 일 N개를 등록하는 시간 | `todo` 앱에 직접 입력 | 대화 후 옮기기 |
| 누른 횟수·입력한 글자 수 | 측정 | 측정 |
| 놓친 할 일 | 사람이 떠올리지 못한 것 | AI가 놓친 것 |

측정 방법과 성공 기준 숫자는 문제 정의서에서 정한다([07 Q-20](07-open-questions.md)).

### 5.3 모델 비교

[07 Q-13](07-open-questions.md)의 후보 모델별 결과를 나란히 둔다: 추출 정확도, 첫 글자까지 걸린 시간, 초당 토큰, GPU 메모리. "왜 이 모델을 골랐는지"의 근거가 된다.

### 5.4 실패 사례

틀린 샘플을 종류별로 묶는다. 예: 날짜 표현 오해, 부정문("안 해도 돼")을 할 일로 뽑음, 남의 일을 내 할 일로 뽑음, 하위 태스크를 따로 뽑음. 한계와 다음 단계 정리에 쓴다.

## 6. 보안 신호 탭

종류와 횟수만 본다.

| 신호 | 뜻 |
|---|---|
| 주소 검사 거부 | 허용되지 않은 업스트림 주소를 넣은 횟수 |
| 요청 횟수 제한 초과 | 남용 가능성 |
| CSRF 거부 | 다른 사이트에서 온 변경 요청 |
| 로그인 실패 | 구글 로그인 과정 실패 |
| LLM 제안 버림 | 스키마에 안 맞거나 남의 태스크를 가리킨 제안 |
| 의존성 점검 결과 | 마지막 점검 시각과 발견 수 (CI 결과 링크) |

## 7. 데이터 수집

### 7.1 무엇을 기록하나

`metric_events` 표 한 행 = 요청 한 번. ([03 5.2](03-architecture.md))

| 열 | 예 |
|---|---|
| `at` | 2026-11-17 21:04:11 |
| `kind` | `chat`, `extract`, `tts`, `stt`, `calendar`, `diary_save`, `hive_register` |
| `ttfb_ms` | 1820 |
| `total_ms` | 6400 |
| `tokens_out` | 152 |
| `status` | `ok`, `timeout`, `upstream_unreachable`, `bad_json`, `google_error`, `rejected_url`, `rate_limited` |

기록하지 않는 것: 사용자·세션 구분 값, 업스트림 주소, 본문, 제목, IP.

### 7.2 어떻게 모으나

- 서버가 요청을 처리하면서 시간을 재고 응답을 보낸 뒤에 기록한다. 기록이 실패해도 사용자 요청에는 영향이 없다.
- TTS 지연처럼 브라우저에서만 알 수 있는 값은 브라우저가 숫자만 `/api/metrics/client`로 보낸다. 서버가 범위를 검사한다.
- 화면은 `/api/admin/metrics?range=7d`로 집계된 숫자만 받는다.
- 그래프는 외부 라이브러리 없이 SVG로 그린다(CSP 유지). 색은 라이트·다크 테마를 따른다.

### 7.3 접근 제어

1. 구글 로그인 세션이 있어야 한다.
2. 가린 구글 ID가 `ADMIN_SUB_HASHES`에 있어야 한다.
3. 아니면 404.
4. 관리자 API도 CSRF와 요청 횟수 제한을 받는다.
5. 로컬 개발에서는 `APP_ENV=development`일 때만 로그인 없이 열 수 있다.

| 1단계 | 지표 기록, PoC 검증 결과 JSON, 검증 탭의 표(로컬에서 열람) |
