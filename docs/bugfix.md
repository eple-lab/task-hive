## BUG-001

**로그아웃 후 로그인 화면에 이전 이메일이 남음**

| 항목 | 내용 |
|---|---|
| 발견 | 2026-10-31, Render 운영 서버에서 회원가입 → 로그아웃 (eple) |
| 영향 | Supabase 모드 화면. 같은 컴퓨터를 다른 사람이 쓰면 직전 사용자의 이메일이 보인다 |
| 심각도 | 낮음 (비밀번호·토큰은 남지 않음) |
| 파일 | [public/app.js](../public/app.js) `showApp()` |

### 재현
1. 로그인 화면에서 이메일·비밀번호 입력 → 회원가입(또는 로그인)
2. 할 일 화면에서 **로그아웃**
3. 로그인 화면 이메일 칸에 1번의 이메일이 그대로 있다

페이지를 새로고침한 뒤 로그아웃하면 칸이 새로 그려져서 재현되지 않는다. **같은 페이지에서 로그인 → 로그아웃**할 때만 생긴다.

### 원인
로그인에 성공하면 `showApp()`이 화면을 할 일 화면으로 바꾸는데, 로그인 폼은 숨기기만 하고 **비밀번호 칸만 비웠다**. 숨겨진 이메일 칸에 값이 남아 있다가, 로그아웃 때 `showAuth()`가 폼을 다시 보여 주면서 그대로 드러났다.

### 수정
`showApp()`에서 이메일 칸도 비운다.

```js
// 2026-10-31 버그 수정: 이메일 칸도 비운다. 안 비우면 로그아웃 후 로그인 화면에 이전 이메일이 남는다 (docs/bugfix.md BUG-001)
$('auth-email').value = '';
$('auth-password').value = '';
```

이메일은 어디에도 저장하지 않는다(공용 PC 고려). 로그인에 성공해 폼을 떠날 때 이메일·비밀번호 칸을 모두 비우므로, 로그아웃이나 세션 만료로 로그인 화면에 돌아와도 칸은 비어 있다.

### 확인
페이지 안에서 `fetch`를 가짜 응답으로 바꿔 로그인 → 로그아웃만 실행했다. 실제 계정 정보는 네트워크로 보내지 않았다.

| 대상 | 로그아웃 후 이메일 칸 |
|---|---|
| 수정 전 (Render) | `mock@example.com` 남음 |
| 수정 후 (로컬) | 빈 칸 |

- [x] 로컬 수정본 확인
- [ ] Render 자동 배포 후 실제 로그인 → 로그아웃으로 다시 확인

테스트 전체 결과는 [test-report-2026-10-31.md](test-report-2026-10-31.md).

## BUG-002

**RLS 확인 스크립트: 대조군 제목 때문에 거짓 FAIL, 실패 시 정리 누락**

| 항목 | 내용 |
|---|---|
| 발견 | 2026-10-31, 보강한 `npm run check:rls` 첫 실행 (18/19, eple 실행) |
| 영향 | 테스트 스크립트만. 앱과 RLS 정책에는 문제 없음 |
| 심각도 | 중간 (RLS가 뚫린 것처럼 보이는 거짓 결과, 실패 시 테스트 데이터가 남을 수 있음) |
| 파일 | [scripts/rls-check.mjs](../scripts/rls-check.mjs) |

### 배경
처음 스크립트(15개 검사)는 B 쪽 대조군이 없었다. B의 목록이 비어 있으면 "A의 것을 못 본다"와 "아무것도 못 본다(고장)"를 구분할 수 없어서, B도 자기 할 일을 하나 만들고 다음 4개를 추가했다(19개).
- [서버] B의 목록에 B의 할 일은 있다 (대조군)
- [서버] A의 목록에 B의 할 일이 없다 (반대 방향)
- [직접] B가 자기 할 일 조회 → 1행 (대조군)
- [직접] A가 B의 할 일 조회 → 0행 (반대 방향)

### 증상
```
FAIL  [서버] B가 A의 제목으로 검색해도 안 나온다  (1건)
결과: 18/19 통과
```

### 원인
1. **거짓 FAIL**: B의 대조군 제목을 `${marker} (B)`로 만들어 A의 제목 문자열(`marker`)이 그대로 들어 있었다. B가 `marker`로 검색하면 **B 자신의 할 일**이 1건 잡히는데, 검사는 "0건인가"로 판정했다.
2. **정리 누락**(코드 검토 중 발견): B의 할 일 생성이 `try` 밖에 있어서, 여기서 실패하면 `finally`가 실행되지 않아 A의 확인용 할 일이 지워지지 않고 남는다.

### RLS가 뚫리지 않았다는 근거 (같은 실행)
| 검사 | 결과 |
|---|---|
| [서버] B의 목록에 A의 할 일이 없다 | PASS (A의 #5 없음) |
| [직접] B가 A의 할 일 조회 → 0행 | PASS |
| [서버] B의 목록에 B의 할 일은 있다 | PASS (B의 목록 1개 = B의 #6) |

검색 결과 1건이 B의 #6이라는 건 위 결과로 본 **추론**이다. 당시 스크립트는 검색 결과의 id를 출력하지 않았다.

### 수정
- B의 대조군 제목을 `RLS 대조군 B <시각>`으로 바꿔 `marker`를 넣지 않는다. 검색 검사는 원래대로 **0건** 기준을 유지한다.
- 검색 결과가 있으면 id를 함께 출력해 다음에 원인을 바로 알 수 있게 한다.
- B의 할 일 생성을 `try` 안으로 옮기고, `finally`에서 B의 할 일은 만들어졌을 때만 지운다.
- 코드에 `2026-10-31 BUG-002` 주석을 남겼다.

검토 중 결정한 것: 처음에는 검색 검사를 "A의 id가 결과에 없는가"로 바꾸는 방법도 있었지만, "B가 A의 문자열로 검색하면 0건"이 더 엄격하고 읽기 쉬워서 대조군 제목을 바꾸는 쪽을 택했다.

### 확인
- [x] 수정본 문법 검사 (`node --check`), 검사 19개
- [x] `npm run check:rls` 재실행 → **19/19 통과** (2026-10-31, eple 실행). 검색 검사 0건 PASS

### 참고: 남겨 둔 약점
- "[직접] B가 완료 함수로 A의 할 일 완료 → 효과 없음"은 에러가 없는지만 본다. 실제로 효과가 없었다는 건 마지막 "[확인] A의 할 일이 그대로 있다(완료=false)"가 간접적으로 확인한다. 처음 스크립트부터 그랬고, 이번에는 바꾸지 않았다.

## BUG-003

**태스크 등록 후, 그리고 다른 계정으로 바꿔도 등록창·검색 상태가 남음**

| 항목 | 내용 |
|---|---|
| 발견 | 2026-10-31, Render 운영 서버 (eple). ① `aaa`로 태스크 등록 후에도 "태스크로 등록" 체크와 라디오 목록이 그대로 ② `aaa` 로그아웃 → `bbb` 로그인했는데 체크가 켜진 채 |
| 영향 | 모든 모드 화면. Supabase 모드에서는 **앞 사용자가 입력하다 만 제목과 검색어가 다음 사용자에게 보임** |
| 심각도 | 중간 (공용 PC에서 개인정보 노출, 다음 사용자의 목록이 앞 사용자의 검색·필터로 걸러져 비어 보임) |
| 파일 | [public/app.js](../public/app.js) |

### 조사: 사용자가 바뀌어도 남던 상태
로그인 화면으로 바뀔 때 할 일 화면을 **숨기기만** 하고 값은 그대로 두었다. 같은 페이지에서 다음 사람이 로그인하면 그대로 다시 보였다.

| # | 상태 | 남았을 때 문제 |
|---|---|---|
| 1 | "태스크로 등록" 체크 | eple이 발견 |
| 2 | 라디오 목록 표시, 마감일 칸 숨김, 안내 문구 | 1을 따라 남음 |
| 3 | 라디오 선택 | 앞 사용자 기준 선택 |
| 4 | 입력하다 만 제목 | **A가 쓰던 글이 B에게 보임** |
| 5 | 검색어 | **A의 검색어가 보이고, B의 첫 목록 요청에 적용됨** (`GET /api/todos?q=A의&today=1`) |
| 6 | "오늘 할 일만" 체크 | B의 목록이 걸러짐 |
| 7 | 마감일 값 | A가 고른 날짜 |

태스크를 등록한 직후에도 1~3이 남았다. 연속 입력을 염두에 둔 동작이었지만, 등록이 끝나면 처음 상태로 돌아가는 게 맞다.

### 수정
- `setTaskMode(on)`: 등록창을 할 일·태스크 입력 상태로 바꾸는 코드를 한 곳에 모았다. 끌 때는 라디오 선택도 지운다.
- `resetView()`: 위 7가지 상태와 목록, 라디오 목록, 안내 문구, 대기 중인 검색을 모두 처음으로 되돌린다.
- 호출 시점
  - 로그아웃·세션 만료(401) → `showAuth()`에서
  - 앱 시작 → 브라우저가 새로고침 때 체크박스·입력값을 되살리는 경우까지 막음
  - 태스크 등록 **성공** → `setTaskMode(false)`. **실패**하면 그대로 두어 다시 시도할 수 있게
- 코드에 `2026-10-31 BUG-003` 주석

### 확인
화면 테스트 [test/ui/form-state.check.js](../test/ui/form-state.check.js)를 가짜 Supabase 주소로 켠 서버에서 실행했다. 페이지의 `fetch`를 가짜 백엔드(사용자 A·B)로 바꿔 돌리므로 실제 계정과 Supabase는 쓰지 않는다.

| 대상 | 결과 |
|---|---|
| 수정 전 | **6/15** (U1 4개, U4 4개, U5 1개 실패. B의 첫 목록 요청이 `?q=A의&today=1`, B의 목록이 비어 보임) |
| 수정 후 | **15/15** |

그 밖에 직접 확인한 것
- 로컬 SQLite 서버(임시 DB)에서 할 일 등록 → "태스크로 등록" 체크 → 라디오 선택 → 태스크 등록: 체크 해제, 라디오 숨김, 마감일 칸 다시 보임
- 데모 모드(`?demo`): 같은 흐름 동작, 예시 데이터·안내 문구 정상
- API 자동 테스트 `npm test` 14/14 (화면 수정과 무관함을 확인)

- [x] 로컬 수정본 확인
- [ ] Render 배포 후 실제 계정(`aaa` → `bbb`)으로 다시 확인 (push 후)
