## 1. 새로고침해도 남아야 할 데이터는? 백엔드와 DB는 각각 무슨 일을? (sec_1~3)

**데이터**
- 할 일(제목, 마감일), 그 아래 하위 태스크
- 완료 여부와 **완료한 시각** — 90일 뒤 자동 삭제의 기준이라 함께 남겨야 한다
- (길 B) 할 일의 **주인** — 로그인한 사람마다 자기 할 일만 보여야 하니까

> 검색어, "오늘 할 일만" 체크 같은 건 제외

**백엔드(`server.js`)**
- 요청을 받아서 → 규칙을 검사하고 → 보안 확인하고 → DB에 읽고 쓰고 → 결과를 JSON으로 돌려준다
- 규칙 검사의 예: 마감일이 비었거나 지났으면 거절, 안 끝난 태스크가 있는 할 일을 완료하려 하면 확인 요청(409), 완료된 할 일에는 태스크 추가 금지
- 화면에서도 같은 검사를 하지만, 화면은 사용자가 조작할 수 있으니 **진짜 방어선은 백엔드**

**DB**
- 결과를 남긴다. 서버를 껐다 켜도, 새로고침해도 그대로
- 데이터 모양을 지킨다. 빈 제목, 할 일 없는 태스크, "완료인데 완료 시각 없음" 같은 상태를 DB가 직접 거절한다

## 2. 데이터베이스가 파일 → 관계형 → NoSQL → 클라우드로 발전한 이유 하나 (sec_4)

**관계형(1970, 에드거 코드) RDBMS**
파일에 쭉 적던 시절에는 같은 정보가 여기저기 중복으로 적혀서, 하나를 고치면 나머지와 어긋났다. 코드는 "표로 나누고 표끼리 관계로 잇자"고 제안했다.

태스크마다 할 일 제목을 다시 적는 대신, `tasks` 표에는 `todo_id`(몇 번 할 일인지)만 적었다. 할 일 제목을 고쳐도 한 곳만 바뀌고, 할 일을 지우면 태스크도 함께 지워진다(`ON DELETE CASCADE`).

## 3. 내 Todo 앱의 표·항목·관계는? `SELECT … FROM … WHERE …`를 내 데이터로 (sec_5)

**표 2개, 일대다(1:N)**
- `todos`: id, (길 B) user_id, title, due_date, completed, completed_at, created_at, updated_at
- `tasks`: id, todo_id, title, completed, completed_at, created_at, updated_at
- 할 일 하나에 태스크 여러 개, 태스크 하나는 할 일 하나에만 → 1:N. 태스크는 할 일 없이 존재할 수 없다(`todo_id NOT NULL`)
- 처음엔 마감일·태그를 고민했는데, 태그는 다대다(연결표 필요)라 빼고 **하위 태스크**를 넣었다. 한 표에 `parent_id`를 두는 방법도 있었지만, 표를 나누면 "태스크 아래 태스크"가 구조적으로 생기지 않는다

**내 데이터로 풀어 읽기**
```sql
SELECT title FROM tasks WHERE todo_id = 3 AND completed = false;
```
"태스크 표에서(`FROM tasks`) 3번 할 일에 속하고 아직 안 끝난 것들의(`WHERE`) 제목을 줘(`SELECT`)."
→ 할 일을 완료하려 할 때 "완료하지 않은 태스크가 N개 있습니다" 확인창이 바로 이 질문에서 나온다.

## 4. 로그인한 사용자가 자기 할 일만 보게 하려면? (sec_6)

세 겹으로 막았다.

1. **로그인은 직접 만들지 않는다.** Supabase Auth 사용. 토큰은 화면 자바스크립트가 못 읽는 httpOnly 쿠키에.
2. **할 일마다 주인을 기록한다.** `todos.user_id`의 기본값이 `auth.uid()`라서 서버가 넣지 않아도 DB가 로그인한 사람으로 채운다.
3. **RLS 정책**: `auth.uid() = user_id`인 행만 조회·추가·수정·삭제. 태스크는 "내 할 일에 속한 것만".

> 서버가 **관리자 키(service_role)**로 DB를 부르면 RLS 무시. 서버는 공개 키 + **요청한 사용자의 토큰**으로만 DB를 호출.

확인은 계정 두 개. B로 로그인해서 A의 할 일이 안 보이는지, A의 할 일 번호로 수정·삭제를 보내면 거절되고 원래 할 일은 그대로인지.
자동으로 시험하는 스크립트(`npm run check:rls`)를 클로드가 생성.

## 5. SQL 주입·비밀번호 유출을 막고, 데이터를 복구하려면 AI에게 무엇을 요구할까? (sec_7)

클로드와의 채팅에서 내가 실제로 한 말(원문 그대로)과, 그 결과.

**SQL 주입**
> "5. sql 인젝션은 보완된거야?"

→ 처음부터 파라미터화 쿼리(`?` 자리표)로 되어 있었고, 다시 테스트했다. 제목에 `x'); DROP TABLE todos;--`를 넣으면 그 글자 그대로 저장되고 표는 멀쩡, 검색창에 `' OR 1=1 --`를 넣으면 0건.

**비밀값·경로를 코드에 넣지 않기**
> "내가 만들면 내가 만든 경로를 프로그램 소스에 적어야 되지 않아? 다른사람이 쓰게 할 때는 어떻게 해야하는거지?"

> "아이코 우리 .env파일 안만들었어?"

→ 내 컴퓨터 경로 대신 프로젝트 기준 경로, 사람마다 다른 값은 `.env`로 빼고 `.env.example`(항목 이름만)을 Git에 올린다. `.env`와 DB 파일은 `.gitignore`.

> "sqllite가 프로젝트 파일 안에 들어있어도 되는건가?"

→ 괜찮지만 Git에 올리지 않고, 웹에 공개되는 폴더(`public/`) 밖에 둔다.

**공개 저장소로 올리기 전**
> "미안 우리꺼 프로젝트는 퍼블릭이야"

→ 퍼블릭으로 올리기 전에 커밋 이력 전체에 `.env`나 `.db` 파일이 없는지 확인하고 올렸다.

**데이터를 잃지 않기**
> "맞아 여러사람이 다쓰다가 나 풀나고 우울할거 같아서"

→ 여러 사람이 쓰는 배포는 SQLite 파일 대신 클라우드 DB(Supabase). 다만 Supabase 무료 요금제는 자동 백업이 없어서 직접 백업해야 한다(6번).

**로그인·비밀번호**
작업 전에 다른 세션(DB 전문가로 만든 클로드)에게 먼저 물어봤다.
> "수파베이스하고 수파베이스 어스를 같이쓰면 되나? 예를 들면 투두 앱을 처음엔 에스큐엘 라이트로 할건데 . 다음은 포스트그리 로컬디비에 붙이고 그다음에 수파베이스연결해서 세단계커밋 히스토리를 가지려고 했거든"

→ 둘은 같이 쓰도록 만들어진 것이라 같이 쓰면 된다는 답. Supabase 프로젝트 하나에 PostgreSQL DB와 Auth가 함께 있고, 로그인한 사용자는 같은 DB의 `auth.users` 표에 저장되어 `todos.user_id`가 그걸 가리킬 수 있다.

이 세션에서는 클로드가 길 B를 브리핑할 때 그 방향대로 제안한 것을 확인하고 진행했다.
> "응 B 쪽 해야할거 확인했고 . Supabase, Render 는 내가 가입할게"

→ 로그인은 직접 만들지 않고 Supabase Auth, 비밀번호는 Supabase가 **해시**로 저장(원문을 저장하지 않음), 서버는 관리자 키를 쓰지 않는다.

**다음엔 처음부터 이렇게 요구하기**
- "DB에 넣는 값은 파라미터화 쿼리로. 사용자 입력은 서버에서 다시 검사해 줘."
- "비밀값과 내 컴퓨터 경로는 코드에 넣지 말고 `.env`로. `.env`와 DB 파일은 `.gitignore`에."
- "로그인은 검증된 Auth로. 비밀번호는 해시로."
- "백업 방법과 **복구 방법**을 문서로 남기고, 복구가 실제로 되는지 확인하는 절차도 적어 줘."

## 6. 고른 DB의 무료 한도와 백업 정책 (sec_8)

| | SQLite (길 A) | Supabase Free (길 B) |
|---|---|---|
| 비용·한도 | 내 컴퓨터 파일이라 없음 | DB 500MB, 파일 1GB (강의 기준 2026-02)까지 무료 |
| 주의 | 내 컴퓨터가 꺼지면 끝, 남에게 열 수 없음 | **1주일 안 쓰면 일시정지** → 시연 전에 미리 접속 |
| 자동 백업 | 없음 | **무료 요금제에는 없음** (Pro부터) |
| 내 백업 방법 | 서버 끄고 `todo.db` 파일 복사 | Table Editor에서 CSV 내보내기, 또는 `pg_dump` |

3-2-1 규칙(3벌, 2종류 매체, 1벌은 다른 곳)으로 USB + 외장하드 + 구글 드라이브에 두기로 했다. 가입 직전에 공식 가격 페이지 확인.
