# 오늘의 회고

강의 "백엔드와 데이터베이스 - 데이터가 남는 서비스 만들기"의 회고 질문에 답한 노트.

> **초안이다.** 이 프로젝트에서 실제로 한 일을 바탕으로 정리했다. 내 말투로 고치고, 느낀 점(✍️)은 직접 채운다.

## 1. 새로고침해도 남아야 할 데이터는? 백엔드와 DB는 각각 무슨 일을? (sec_1~3)

**남아야 할 데이터**
- 할 일(제목, 마감일), 그 아래 하위 태스크
- 완료 여부와 **완료한 시각** — 90일 뒤 자동 삭제의 기준이라 함께 남겨야 한다
- (길 B) 할 일의 **주인** — 로그인한 사람마다 자기 할 일만 보여야 하니까

반대로 검색어, "오늘 할 일만" 체크 같은 건 화면에서 잠깐 쓰는 상태라 저장하지 않았다.

**백엔드가 한 일 (`server.js`)**
- 요청을 받아서 → 규칙을 검사하고 → DB에 읽고 쓰고 → 결과를 JSON으로 돌려준다
- 규칙 검사의 예: 마감일이 비었거나 지났으면 거절, 안 끝난 태스크가 있는 할 일을 완료하려 하면 확인 요청(409), 완료된 할 일에는 태스크 추가 금지
- 화면에서도 같은 검사를 하지만, 화면은 사용자가 조작할 수 있으니 **진짜 방어선은 백엔드**다

**DB가 한 일**
- 결과를 남긴다. 서버를 껐다 켜도, 새로고침해도 그대로
- 데이터 모양을 지킨다. 빈 제목, 할 일 없는 태스크, "완료인데 완료 시각 없음" 같은 상태를 DB가 직접 거절한다

## 2. 데이터베이스가 파일 → 관계형 → NoSQL → 클라우드로 발전한 이유 하나 (sec_4)

**관계형(1970, 에드거 코드)을 고른다.**
파일에 쭉 적던 시절에는 같은 정보가 여기저기 중복으로 적혀서, 하나를 고치면 나머지와 어긋났다. 코드는 "표로 나누고 표끼리 관계로 잇자"고 제안했다.

내 Todo 앱에서 그대로 겪었다. 태스크마다 할 일 제목을 다시 적는 대신, `tasks` 표에는 `todo_id`(몇 번 할 일인지)만 적었다. 할 일 제목을 고쳐도 한 곳만 바뀌고, 할 일을 지우면 태스크도 함께 지워진다(`ON DELETE CASCADE`).

## 3. 내 Todo 앱의 표·항목·관계는? `SELECT … FROM … WHERE …`를 내 데이터로 (sec_5)

**표 2개, 일대다(1:N)**
- `todos`: id, (길 B) user_id, title, due_date, completed, completed_at, created_at, updated_at
- `tasks`: id, todo_id, title, completed, completed_at, created_at, updated_at
- 할 일 하나에 태스크 여러 개, 태스크 하나는 할 일 하나에만 → 1:N. 태스크는 할 일 없이 존재할 수 없다(`todo_id NOT NULL`)
- 처음엔 마감일·태그를 고민했는데, 태그는 다대다(연결표 필요)라 빼고 **하위 태스크**를 넣었다. 한 표에 `parent_id`를 두는 방법도 있었지만, 표를 나누면 "태스크 아래 태스크"가 구조적으로 생기지 않는다

**내 데이터로 풀어 읽기**
```sql
SELECT title FROM tasks WHERE todo_id = 3 AND completed = false;
```
"태스크 표에서(`FROM tasks`) 3번 할 일에 속하고 아직 안 끝난 것들의(`WHERE`) 제목을 줘(`SELECT`)."
→ 할 일을 완료하려 할 때 "완료하지 않은 태스크가 N개 있습니다" 확인창이 바로 이 질문에서 나온다.

## 4. 로그인한 사용자가 자기 할 일만 보게 하려면? (sec_6)

세 겹으로 막았다.

1. **로그인은 직접 만들지 않는다.** Supabase Auth가 비밀번호를 해시로 저장하고 토큰을 발급한다. 토큰은 화면 자바스크립트가 못 읽는 httpOnly 쿠키에 둔다.
2. **할 일마다 주인을 기록한다.** `todos.user_id`의 기본값이 `auth.uid()`라서 서버가 넣지 않아도 DB가 로그인한 사람으로 채운다.
3. **RLS 정책**: `auth.uid() = user_id`인 행만 조회·추가·수정·삭제. 태스크는 "내 할 일에 속한 것만".

여기서 배운 함정: 서버가 **관리자 키(service_role)**로 DB를 부르면 RLS가 무시된다. 그래서 서버는 공개 키 + **요청한 사용자의 토큰**으로만 DB를 부른다.

확인은 계정 두 개로 한다. B로 로그인해서 A의 할 일이 안 보이는지, A의 할 일 번호로 수정·삭제를 보내면 거절되고 원래 할 일은 그대로인지. 이걸 자동으로 시험하는 스크립트(`npm run check:rls`)를 만들었다.

## 5. SQL 주입·비밀번호 유출을 막고, 데이터를 복구하려면 AI에게 무엇을 요구할까? (sec_7)

실제로 이 프로젝트에서 요구했고 확인한 것들:

> "DB에 넣는 값은 문자열로 이어 붙이지 말고 파라미터화 쿼리로 처리해 줘. 사용자 입력은 믿지 말고 서버에서 다시 검사해 줘."

→ 제목에 `x'); DROP TABLE todos;--`를 넣어 봤더니 그 글자 그대로 저장되고 표는 멀쩡했다. 검색창에 `' OR 1=1 --`를 넣어도 결과 0건.

> "로그인은 처음부터 만들지 말고 검증된 Auth를 붙여 줘. 비밀번호는 해시로, 토큰은 httpOnly 쿠키에."

> "접속 키는 코드에 넣지 말고 `.env`로 빼고, `.env`와 DB 파일은 `.gitignore`에 넣어 줘. GitHub에 올리기 전에 커밋 이력에 비밀값이 없는지도 확인해 줘."

> "백업하는 방법과 **복구하는 방법**을 문서로 남기고, 복구가 실제로 되는지 확인하는 절차도 적어 줘."

## 6. 고른 DB의 무료 한도와 백업 정책 (sec_8)

| | SQLite (길 A) | Supabase Free (길 B) |
|---|---|---|
| 비용·한도 | 내 컴퓨터 파일이라 없음 | DB 500MB, 파일 1GB (강의 기준 2026-02) |
| 주의 | 내 컴퓨터가 꺼지면 끝, 남에게 열 수 없음 | **1주일 안 쓰면 일시정지** → 시연 전에 미리 접속 |
| 자동 백업 | 없음 | **무료 요금제에는 없음** (Pro부터) |
| 내 백업 방법 | 서버 끄고 `todo.db` 파일 복사 | Table Editor에서 CSV 내보내기, 또는 `pg_dump` |

3-2-1 규칙(3벌, 2종류 매체, 1벌은 다른 곳)으로 노트북 + 외장하드 + 구글 드라이브에 두기로 했다. 정책은 바뀔 수 있으니 가입 직전에 공식 가격 페이지를 다시 확인한다.

## 7. 로컬과 Supabase에서 할 일을 추가하고 새로고침했을 때 남았나? (sec_9)

| | 추가 | 새로고침 후 | 서버 재시작 후 | 기록 |
|---|---|---|---|---|
| 로컬 SQLite | ✅ 할 일 4개, 태스크 8개 | ✅ | ✅ 같은 데이터 그대로, DB 파일에도 4행·8행 | 캡처 3장 (2026-10-30), `feature/path-b-supabase` 브랜치의 `docs/verification.md` |
| Supabase | ⏳ | ⏳ | ⏳ | 실제 프로젝트 연결 후 |
| RLS (계정 B에서 A의 할 일) | | | | ⏳ 메모리 Postgres에서는 통과, 실제 프로젝트에서 `npm run check:rls` 예정 |

## 배운 것 / 어려웠던 것 / 다음에

**배운 것**
- "화면은 백엔드에만, 백엔드만 DB에"를 지키니까 저장소를 SQLite → Supabase로 바꿀 때 `db.js` 한 파일만 크게 바뀌었다
- 같은 규칙을 화면·백엔드·DB 세 겹으로 막는 이유 — 화면은 편의, 백엔드는 방어선, DB는 마지막 안전망
- 커밋을 기능 단위로 나눠 두니(A-1 ~ B-5) 무엇을 언제 바꿨는지 되짚기 쉬웠다. 길 A는 `path-a` 태그로 언제든 돌아갈 수 있다

- ✍️ (예: GitHub Pages에는 서버가 없어서 진짜 앱을 그대로 올릴 수 없다는 것 / RLS를 켜기만 하면 안 되고 정책까지 만들어야 한다는 것)
