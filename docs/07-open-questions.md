### Q-04. "그건 한 것 같아"에서 어디까지 바로 체크할까

| 선택지 | 설명 |
|---|---|

| 항상 바로 체크 | 가장 편하지만 잘못 알아들으면 여러 개가 바뀐다 |

함께 정할 것: LLM은 제안만 하고 서버가 검증해 반영한다(P-06). 삭제는 대화로 하지 못하게 한다.

### Q-13. 어떤 모델을 쓸까 (비교 실험으로 정한다)

과제가 "왜 그 모델을 골랐는지, 다른 후보와 비교"를 요구한다. 실험 전에 후보와 기준만 정한다.

| 역할 | 후보 | 볼 기준 |
|---|---|---|
| 대화·추출 | `llm-chatbot`에서 쓴 Qwen 4B급 AWQ, 그보다 큰 양자화 모델, 한국어 특화 모델 | 한국어 자연스러움, JSON 추출 정확도, 속도, GPU 메모리, 라이선스 |
| TTS | MeloTTS-Korean, Supertonic 2, XTTS-v2, 브라우저 내장 음성(기준선) | 한국어 품질, **남·여 목소리 지원**, 속도, 라이선스 |
| STT (2단계) | Whisper small / medium / large-v3-turbo | 한국어 오류율, 속도, 메모리 |

확인 결과 ([09 확인 기록 2.8](09-verification.md)):

- Kokoro는 한국어를 지원하지 않아 후보에서 뺐다.
- **남·여 한국어 목소리를 둘 다 제공한다고 공식 페이지에서 확인된 모델은 없다.** MeloTTS-Korean은 예제에 화자가 하나만 나온다. Supertonic 2와 XTTS-v2는 목소리 수나 사용 조건을 페이지에서 확인하지 못했다.
- 그래서 실험 순서는 ① 라이선스와 남·여 지원으로 통과/탈락을 먼저 가르고 ② 남은 후보만 품질·속도로 비교한다.

수업 요약에서 가져온 비교 원칙:

- 같은 모델의 크기만 바꾼 후보가 아니라 **성격이 다른 후보**(실행 위치, 만들어진 목적, 결과 형태)를 놓는다.
- **지금 방식(기준선)**을 후보에 넣는다. TTS는 브라우저 내장 음성, 할 일 등록은 `todo` 앱 직접 입력이다.
- 실행 위치와 라이선스는 감점이 아니라 **탈락 조건**이다.
- 한국어는 공개 벤치마크에 없는 경우가 많다. 내 문장으로 직접 넣어 본다.

eple이 써 보고 싶은 모델이 있으면 후보에 넣는다.

### Q-25. Colab 이용 정책 위험을 어떻게 다룰까 (확인 뒤 추가)

Colab FAQ는 대화형 연산과 관련 없는 웹 서비스 제공과, 무료에서 노트북 화면을 거치지 않고 주로 웹 화면으로 쓰는 것을 제한한다. Colab + ngrok으로 LLM을 여는 구조는 여기에 해당할 수 있고 세션이 경고 없이 끊길 수 있다. ([09 확인 기록 2.9](09-verification.md))

| 선택지 | 설명 |
|---|---|
| **Colab을 기본으로 하되 과제·시연 용도로 한정하고, 업스트림을 "OpenAI 호환 주소"로 일반화 (추천)** | 수업에서 배운 방식 그대로다. 같은 게이트웨이를 로컬 PC에서 띄워도 연결되게 해 두면 Colab이 막혀도 갈아탈 수 있다. README에 이 제한을 적는다 |
| Colab만 지원 | 구현이 가장 단순하다. 끊기면 대안이 없다 |
| 로컬 PC(Ollama 등)를 기본으로 | 정책 위험이 없다. GPU가 없는 PC에서는 느리고, TTS·Whisper를 따로 띄워야 한다 |

함께 정할 것: 로컬 주소(`http://localhost`)를 허용하면 주소 검사 규칙(SSRF 방어)이 달라진다. 로컬 실행 모드에서만 허용하는 것을 추천한다.

## 2단계 시작 전에 필요한 질문

### Q-01. 구글 권한과 앱 상태

| 선택지 | 설명 |
|---|---|
| **테스트 상태로 두고 테스트 사용자만 (추천, 과제 기간)** | 검증 절차가 없다. 등록한 계정(최대 100명)만 쓸 수 있고 refresh token이 7일 뒤 만료된다(확인함) |
| 구글 앱 검증 신청 | 누구나 쓸 수 있다. 개인정보처리방침, 도메인, 심사가 필요하다 |

함께 확인할 것: 권한을 `openid` + `drive.file` + `calendar.events.readonly`로 하고(P-01), 구글 이메일·이름을 받지 않는 것(P-02).

확인 뒤 추가된 질문 ([09 확인 기록](09-verification.md) 2.4, 2.5):

| 질문 | 선택지 |
|---|---|
| 구글 토큰을 어떻게 둘까 | **refresh token을 암호화해 저장 (추천)**: 다시 로그인 없이 시트 내보내기가 된다. 테스트 상태에서는 7일마다 재로그인 / refresh token을 받지 않고 1시간짜리 토큰만 (`honey-voice-log` 방식): 서버에 오래 가는 토큰이 없어 더 안전하다. 1시간마다 구글 연결을 다시 눌러야 한다 |
| 캘린더 권한 범위 | **`calendar.events.owned.readonly` (추천으로 변경 제안)**: 내가 소유한 캘린더의 일정만 본다. 공유받은 남의 캘린더는 읽지 않는다 / `calendar.events.readonly`: 볼 수 있는 모든 캘린더의 일정 |
| 캘린더 권한의 민감 분류 | 공식 문서에 표시가 없다. eple이 Google Cloud Console 동의 화면에 권한을 추가해 표시를 확인해야 한다 |

### Q-07. 일기 파일 구조

"폴더 하위에 월로 구분"의 풀이가 여러 가지다.

| 선택지 | 설명 |
|---|---|
| **월별 파일 하나씩 (`2026-11`), 하루 한 행 (추천)** | 폴더에 달마다 파일이 생긴다. Docs를 골라도 같은 규칙(월별 문서, 날짜별 제목) |
| 연도별 파일 하나 + 월별 탭 | 파일 수가 적다. Docs에는 탭 구조가 달라 규칙이 갈린다 |
| 하루 한 파일을 월별 하위 폴더에 | 가장 잘게 나뉜다. 파일이 많아진다 |

함께 정할 것:

- 하루에 여러 번 적으면: **같은 날 행에 덧붙이기(추천)** / 덮어쓰기 / 새 행

### Q-08. Docs에 이미지 올리기

구글 Docs에 이미지를 넣는 것 자체는 가능하다. 다만 Docs API는 이미지를 **공개 주소**로 받아 넣는 방식이라(확인함: 공개 접근 가능한 주소, 50MB 미만, PNG·JPEG·GIF), 사용자의 사진을 잠깐이라도 공개 주소에 올려야 한다.

| 선택지 | 설명 |
|---|---|
| **1단계 Docs 일기는 글만, 이미지는 방식을 확인한 뒤 2단계 이후 (추천)** | 개인정보 위험을 확인하고 넣는다 |
| 드라이브에 올리고 링크만 넣기 | 공개하지 않는다. 문서 안에 그림이 보이지는 않는다 |
| 잠깐 공개 주소로 올려 넣고 바로 지우기 | 문서 안에 그림이 보인다. 짧은 시간 공개된다 |

함께 물을 것: 어떤 이미지를 올리려는 것인가 (사용자가 고른 사진 / AI가 만든 그림 / 벌집 화면 캡처).
